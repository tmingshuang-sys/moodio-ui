## 上线

```bash
npm run deploy
```

它做五件事，每一步不过就停：本地跑 tsc + 测试 → 确认没有未提交的改动 → push 到 GitHub → 服务器拉代码重新构建重启 → 自检外网能不能打开、线上跑的 commit 是不是刚推的那个。

整个过程两三分钟，大部分时间花在服务器上 `npm install` 和构建。

**手动来一遍**（deploy 脚本挂了的时候）：

```bash
workbench exec -i i-j6c5drkfd0v4igyewyie -r cn-hongkong --command \
  'su - wow -c "cd /opt/wow && git fetch --depth 1 origin main -q && git reset --hard -q origin/main" && \
   cp /opt/wow/server/deploy/setup.sh /tmp/s.sh && \
   setsid nohup bash /tmp/s.sh --domain 47-238-73-78.sslip.io > /tmp/d.log 2>&1 & sleep 2; echo 开始'
```

然后 `tail -f /tmp/d.log` 看进度。

### 部署与渲染里几个反直觉的地方

这两个都是实际踩出来的，别「优化」掉：

1. **`setup.sh` 开头把自己拷到 `/tmp` 再 `exec`。** 因为它跑到一半会 `git reset --hard` 掉自己，而 bash 是按字节偏移边读边执行的 —— 文件在运行中变了长度就会跳到错位置。症状是装完打出来的是上一版的文案，而且中间的步骤被悄悄跳过。

2. **取代码用 `FETCH_HEAD`，不是 `origin/<分支>`。** 机器上是浅克隆（`--depth 1 -b xxx`），origin 只配了那一个分支的 refspec，换分支时 `origin/<新分支>` 这个远程跟踪引用根本不存在，`git reset --hard origin/main` 会报 `ambiguous argument`。2026-10-31 从 redesign 换到 main 时踩到过，部署会卡在那里。

3. **管道里不要接 `head`。** `set -euo pipefail` 下，`systemctl list-timers | head -2` 这种写法会让 systemctl 收到 SIGPIPE 退出非零，`pipefail` 把它传出来，`set -e` 当场结束整个脚本 —— 后面的 Caddy 配置和自检全都不跑。表现是「装完了但没打总结」，而服务其实已经起来了，属于最难察觉的半截成功。要截断就加 `|| true`，或者用命令自己的参数（`--no-legend`）。

4. **systemd 那一步是 `enable` + `restart`，不是 `enable --now`。** `--now` 对已经在跑的服务什么都不做，于是「更新代码」只更新了磁盘上的文件，进程还是旧的，库迁移也不会跑（迁移在 `index.mjs` 启动时执行）。

5. **出片的 Chromium 必须带 `--font-render-hinting=none`。** 渲染字体已经随页面发（同一份 woff2），但 Linux 上 headless Chromium 默认对 webfont 开 full hinting，把每个字宽取整：同一句 64px 混合串 Mac 量出 1974.336、服务端带参数 1974.332、不带参数 1977。差这 3 px 折行就可能比预览多一行。上游 `core/render/browser.mjs` 的 ARGS 里已经有这个参数，出片走 `page.mjs` 不用管；**自己另起 Chromium 量字宽或截帧时记得带上**，不然量出来的不是成片的字宽。

## 备份

### 自动

每天凌晨 3:30（加最多 30 分钟随机延迟）跑一次，存在 `/var/backups/wow`，留最近 7 份。机器那天没开的话，开机后会补跑（`Persistent=true`）。

```bash
systemctl list-timers wow-backup.timer    # 看下次什么时候跑
journalctl -u wow-backup.service -n 30    # 看上次跑得怎么样
```

每份备份里有：数据库全量（`pg_dump -Fc`）、媒体文件（`blobs.tar.gz`，媒体切到 OSS 之后这里基本是空的）、`.env`、当时的代码版本号。

### 异地（2026-10-31 起自动）

本机那份和数据在同一台机器上，防的是「删错了、库坏了」，防不了「机器没了」。所以 `backup.sh` 做完本机那份之后会**再传一份到 OSS**（`wow-media-hk` 的 `backups/` 下，服务端加密，生命周期 30 天自动过期），凭实例角色上传，不经过任何密钥。传没传成功在网页「服务器设置 → 系统状态 → 上次备份」一眼能看到（没传到 OSS 会标红）。

```bash
# 看 OSS 里有哪些备份（在服务器上）
workbench exec -i i-j6c5drkfd0v4igyewyie -r cn-hongkong --command 'su - wow -c "cd /opt/wow/server && npm run -s oss:backups"'
# 从 OSS 拿一份回服务器（恢复用）
workbench exec -i i-j6c5drkfd0v4igyewyie -r cn-hongkong --command 'cd /opt/wow/server && node --env-file=.env scripts/oss-backup.mjs download backups/wow-20261101-033000.tar.gz /var/backups/wow/wow-20261101-033000.tar.gz'
# 或者直接拉到自己电脑（本机 aliyun CLI 的 site-deploy 有 OSS 权限）
aliyun oss cp oss://wow-media-hk/backups/wow-20261101-033000.tar.gz ~/WoW备份/ -e oss-cn-hongkong.aliyuncs.com
```

自己电脑上的 `npm run backup` 仍然可以用（让服务器现做一份并下载到 `~/WoW备份/`），当第三份。

> ⚠️ 备份文件里有密钥：模型 key 在库的 `settings` 表里是明文存的，`.env` 里有数据库密码和网关口令。文件权限是 600，别往公开的地方放、别传到网盘的公开目录。

### 恢复

```bash
# 在服务器上
sudo bash /opt/wow/server/deploy/restore.sh --latest
# 或者指定某一份
sudo bash /opt/wow/server/deploy/restore.sh /var/backups/wow/wow-20261101-033000.tar.gz
```

它会先把当前状态另存一份再动手，所以恢复错了还能退回去。`.env` 不会自动覆盖（现在这台机器的数据库密码可能和备份时不一样，盖回去反而连不上库），备份里的那份会放在 `/var/backups/wow/env-from-backup` 供参考。

**没恢复过的备份不算备份。** 装好之后至少演练一次。

## 账号

第一个账号（装机时用一次性口令建的）是**管理员**，只有它能改「服务器设置」里的东西（模型 key、邀请码、OSS、账号）。其他账号只能看自己的创作。

- **开放注册**：服务器设置 → 账号 → 填一个邀请码保存。想注册的人在登录框点「没有账号？用邀请码注册」，邮箱 + 密码 + 邀请码。把邀请码清掉（填一个空格再保存）就关闭注册。
- **别人忘了密码**：服务器设置 → 账号 → 账号列表里点那个人后面的钥匙图标 → 复制链接发给对方。链接 **24 小时有效、用一次作废**，对方打开后自己设新密码，设完直接是登录态；这个人原来所有已登录的会话一并作废。没有邮件服务，链接是人传人——这是有意的，少一个外部依赖。
- **管理员自己忘了密码**：在服务器上给自己生成一条：

  ```bash
  workbench exec -i i-j6c5drkfd0v4igyewyie -r cn-hongkong --command 'su - wow -c "cd /opt/wow/server && npm run -s reset:link -- 你的邮箱"'
  ```

  把打出来的 `/?reset=…` 接在站点地址后面打开。
- **自己改密码 / 改称呼**：服务器设置 → 我的账号。改密码要先输当前密码，改完其他设备上的登录全部失效、当前这个保留。
- **停用账号**：管理员在账号列表点那个人后面的「停用」图标——登不进、已登录的全部失效、数据原样保留，随时可以再点「启用」。不能停用自己。
- 猜邀请码和猜重置链接都按 IP 限流：10 分钟内错 5 次挡 1 小时（和初始化口令一样），`systemctl restart wow-server` 即清零；自己改密码时当前密码猜错也计入登录那个桶。

## 媒体存储（OSS）

**现状（2026-10-31 接好）**：bucket `wow-media-hk`（中国香港、私有），服务器凭 ECS 实例角色 `WowOssRole` 访问（`AliyunOSSFullAccess`），走内网 endpoint `oss-cn-hongkong-internal.aliyuncs.com`；四项配置写在 `/opt/wow/server/.env`（`OSS_BUCKET` / `OSS_REGION` / `OSS_ENDPOINT` / `OSS_ROLE`，都不是密钥）。在线上用服务端自己的 `oss.mjs` 做过 上传→查→下载→删 一轮（214 ms），`/health` 的 `storage` 是 `{kind: oss, ok: true, auth: role}`。切换时本机 blobs 目录是空的，没有东西要搬。

下面是从零再做一遍的步骤（换账号、换 bucket 时用）。图片 / 视频 / 成片的**文件**默认在服务器本机 `/opt/wow/server/blobs/`（库里只记键名），40G 会满：

1. **OSS 控制台建 bucket**：地域选**中国香港**（和 ECS 同区域，走内网不计流量），读写权限选**私有**，别开公共读。记下 bucket 名和地域 id（`oss-cn-hongkong`）。
2. **凭证用「实例角色」，不用 AccessKey**（推荐）：RAM 控制台 → 角色 → 创建角色 → 可信实体选「阿里云服务」→ 普通服务角色 → 受信服务选「云服务器」→ 角色名 `WowOssRole` → 创建后给它添加权限 `AliyunOSSFullAccess`（之后可以收成只管这一个 bucket 的自定义策略）。然后把角色挂到这台 ECS（控制台：实例 → 更多 → 实例设置 → 授予 / 收回 RAM 角色；或者有 ECS 权限的 key 跑 `aliyun ecs AttachInstanceRamRole --RegionId cn-hongkong --InstanceIds '["i-j6c5drkfd0v4igyewyie"]' --RamRoleName WowOssRole`）。机器会自己向元数据服务（`100.100.100.200`）领几小时一换的临时凭证，**库里、.env 里、对话里都不存任何密钥**。
   没法用角色时的退路：建一个只有这个 bucket 权限的 RAM 子账号，创建 AccessKey，填进下一步的 AccessKey 两栏——Secret 只显示一次，直接粘进网页，不要存在聊天记录里。
3. **网页「服务器设置 → 媒体存储」**填 bucket、区域、实例角色名 `WowOssRole`（或 AccessKey 两栏），Endpoint 填 `oss-cn-hongkong-internal.aliyuncs.com`（同区域内网）。保存后状态栏「存储」变成 `OSS · bucket名`；连不上会把原因写出来（角色没挂上 / AK 不对 / 没权限 / bucket 或区域不对），上游真实的错误码在服务日志里。
4. **把老文件搬过去**（可选，不搬也能读）：

   ```bash
   workbench exec -i i-j6c5drkfd0v4igyewyie -r cn-hongkong --command 'su - wow -c "cd /opt/wow/server && npm run -s blobs:migrate"'
   ```

   逐个上传、校验大小一致后才删本机那份；加 `-- --keep` 只上传不删。可以反复跑。

**已删媒体的文件会自动清**：前端删除是软删（回收站 7 天可恢复），服务端只记 `deleted_at`；服务进程每天跑一次清理，把删掉超过 30 天的媒体对应的对象从 OSS 删掉（行留着、`object_key` 置空、记 `purged_at`，同步才知道这条删过）。想立刻跑：`npm run purge`（在 `/opt/wow/server` 下）。待清理的数量在「系统状态 → 账号 / 创作」那格里。

两条原则：配了 OSS 就**只往 OSS 写**，写不进去直接报错，绝不悄悄退回本机磁盘（那样文件散两处，重装机器就丢）；读的时候 OSS 里没有才看本机磁盘（过渡期）。`/health` 的 `storage` 字段能看到当前用的是哪种、通不通。

签名是自己写的（`server/src/oss.mjs`，V4，不装 SDK），用官方 SDK 的测试向量钉着；文件走服务器中转（浏览器 → 后端 → OSS），bucket 不用公共读。

## 出事了怎么办

### 先看「系统状态」

网页 → 侧栏设置 → 服务器设置 → 系统状态：六个格子，红的就是要管的——磁盘 ≥ 85%、备份超过 36 小时没跑或没传到 OSS、OSS 连不上、渲染任务 7 天内有失败。数据来自 `/api/admin/status`（磁盘 `statfs`、`server/.backup-status.json`、OSS 列目录、库里的计数、`.git/HEAD`）。

### 页面打不开

```bash
workbench exec -i i-j6c5drkfd0v4igyewyie -r cn-hongkong --command '
  systemctl status wow-server --no-pager -l | head -20
  systemctl status caddy --no-pager | head -5
  curl -fsS --noproxy "*" http://127.0.0.1:8787/health; echo
  journalctl -u wow-server -n 40 --no-pager'
```

- 后端自己（8787）通、外网不通 → Caddy 的问题，`journalctl -u caddy -n 50`
- 两边都不通 → `systemctl restart wow-server`
- 证书问题 → 确认安全组放行了 80 和 443（续期要走 80）

### 被 429 挡住了

限流只拦失败的请求，所以正常用不会撞上。真撞上了：

- **登录 429**（挡 15 分钟）：密码连错 8 次。等着，或者在服务器上清掉——重启服务即可，限流是内存里的：`systemctl restart wow-server`
- **网关 429**（挡 2 分钟）：口令连错 30 次。最常见的原因是在「服务器设置」里改了网关口令，但页面的「模型设置」里还是旧的。把两边改成一致，口令一对就立刻解封，不用等

### 模型调用报错

先看 `/health` 里那几个 key 是不是 `true`：

```bash
curl -s https://47-238-73-78.sslip.io/health
```

`false` 就是没配，去网页的「服务器设置」里填，填完即时生效不用重启。都是 `true` 还报错，就是上游的问题（余额、限流、模型下线）。

### 磁盘满了

```bash
workbench exec -i i-j6c5drkfd0v4igyewyie -r cn-hongkong --command 'df -h /; du -sh /opt/wow/server/blobs /var/backups/wow'
```

40G 里大头是媒体文件和备份。应急：把 `KEEP` 调小、删掉老备份。根治：把媒体文件切到 OSS，见下面「媒体存储（OSS）」。

### 数据对不上 / 同步不动

同步状态在网页「服务器设置」里能看到。同步是 last-write-wins，两台机器同时改同一份文稿，晚改的赢，不做合并也不提示。

```bash
# 看库里到底有什么
workbench exec -i i-j6c5drkfd0v4igyewyie -r cn-hongkong --command \
  'su - postgres -c "psql -d wow -tAc \"select p.title, count(d.id) from projects p left join docs d on d.project_id=p.id group by p.title\""'
```
